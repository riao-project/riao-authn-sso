# @riao/authn-sso

Framework-neutral OAuth2/OIDC authentication base for provider drivers.

## Version 3 migration

Requires `@riao/iam ^5.0.0`; provider packages also move to version 3.
Run IAM migrations first, then the complete SSO migration package before
admitting any v3 authentication traffic.

`SSOAuthenticationOptions` extends IAM `AuthenticationOptions`, including
`authenticationProtection`. Provider wrappers forward every inherited option:
`stateExpiryMinutes` (default 10), `requestTimeoutMs` (default 10,000 ms),
encryption keys, and protection.

```typescript
const { url, state } = await auth.generateAuthorizationUrl();
// Redirect to url. Pass the callback state when the provider returns it.
const principal = await auth.authenticate({ code, state });
if (principal) {
	// Store the authenticated principal in the application session.
}
```

Authentication requires a code and a non-empty state. State
must be generated by this driver, is provider-scoped, expires, and is consumed
before code exchange. State is claimed atomically so concurrent callbacks
have only one winner. State is not bound to a browser session; applications
must enforce that binding separately.
Do not call `validateState` separately before `authenticate`: it consumes state.
Invalid, expired, or replayed state returns `null` from authentication.
Direct `validateState` calls throw IAM `AuthenticationRejectedError`.
Code exchange failure still consumes state; start a fresh authorization flow.

## Protection and errors

- `beforeAttempt` runs once before state validation and provider requests.
  Denial returns `null`, with neither `onFailure` nor `onSuccess`.
- Missing credentials, state rejection, expected provider rejection, and an
  inactive principal call `onFailure` once and return `null`. Existing inactive
  principals are never replaced by new provisioning.
- Success calls `onSuccess` once, after tokens have been persisted.
- `AuthenticationBlockedError` returns `null` without recording a failure.
- Operational errors (transport, outage, database,
  or callback failure) propagate without `onFailure`.

Attempts use `{ scheme: 'sso:<provider>', subject: '<provider>' }` consistently,
because local identity is unknown before exchanging the code. Protection is
provider-scoped; applications can layer browser/IP-specific protection outside
the driver. Attempts never include authorization codes, state, or tokens.

Exchange/refresh/userinfo APIs retain their response shapes and throw
`ProviderAuthenticationRejectedError` for known provider credential rejection.
Invalid client configuration, permission failures, throttling and outages
remain operational. Provider HTTP errors omit raw response bodies.
Direct APIs preserve typed errors; `AuthenticationBlockedError` can carry
`retryAfterSeconds`. Authentication's `null` does not carry retry timing.

At HTTP boundaries, translate rejection to a generic authentication failure,
blocked errors to a suitable rate-limit response (optionally `Retry-After`),
and operational errors to a generic server/unavailable response. Do not return
or log credentials or unfiltered provider/database errors to users.
Use HTTPS and a production session store.

## Provider Request Safety

Provider adapters can opt in to bounded requests by calling `requestProviderJson` with the configured `requestTimeoutMs` (default: 10,000 ms), and validate decoded responses with `validateTokenResponse` and `validateProviderUser`. The request and response-classification helpers report expected credential rejections as `ProviderAuthenticationRejectedError`; malformed responses, timeouts, and other provider failures remain operational errors. These protections apply only to adapters that adopt the helpers; this change does not update existing adapters.

Existing adapters can use the exported `throwProviderResponseError` helper to classify HTTP response failures without adopting the request helper.

`requestProviderJson` preserves a caller-provided `options.signal` alongside its timeout signal. Either cancellation source aborts the request.

Provider-facing error messages omit response bodies and transport details. Their `cause` is retained for trusted server-side diagnostics and should not be returned to clients.

## SSO Callback State

Always generate state before redirecting to the identity provider and pass the callback's non-empty `state` value to `authenticate`. Missing, invalid, expired, or reused state is rejected before authorization-code exchange.
